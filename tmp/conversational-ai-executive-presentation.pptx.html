Design Principle

"The LLM decides what to request and how to respond conversationally. Deterministic server code decides how data is retrieved, validated, merged, and rendered."

AI Handles

  • Understanding shopper intent
  • Choosing which tools to call
  • Generating natural responses
  • Product comparison analysis
  • Guiding support conversations

Deterministic Code Handles

  • Data retrieval via GraphQL
  • Filter merge across turns
  • Authentication injection
  • Ticket form rendering
  • UI card and grid rendering

Product Search and Discovery

How It Works

  • Shopper types: "black running shoes under $100"
  • AI extracts: query, color, price range
  • Server calls UACAPI with structured filters
  • Widget renders product cards with image, price, rating, colors, sizes

Multi-Turn Refinement

  • Filters accumulate: "running shoes" → "under $100" → "only black"
  • Server-side deterministic merge, not LLM memory
  • Dynamic refine chips from live UACAPI data
  • reset: true clears for new context

Help and Support — Hybrid AI + Deterministic

Two entry points: conversational in-chat flow and standalone Help drawer.

Step Driven By What Happens
1. Category LLM + chips Order, Payment, Product, Return/Refund, Other
2. Order selection LLM + chips Fetches recent orders as selectable chips
3. Resolution LLM + chips Shows tracking, asks if resolved
4. Ticket creation Deterministic form Fixed React form — description + email + submit

Why Step 4 is deterministic: LLM was unreliable for multi-step data collection — skipping steps, creating tickets without descriptions. The server intercepts create_support_ticket and renders a fixed React form instead. Reliable every time.

End-to-End Request Lifecycle

1. Shopper Message
Types query in chat widget
2. Widget Resolves Context
Auth token, locale, customer ID
3. POST /agent/stream
SSE connection to backend
4. Agent Builds Messages
System prompt + history + filters + request
5. LLM Selects Tools
MCP tools validated + auth injected
6. UACAPI GraphQL
Static queries + variables only
7. Stream Results
Products/orders stream as tools complete
8. Widget Renders
Cards, grids, drawers — structured data, not LLM markup

MCP Tools — Read-Only by Design

All tools are annotated readOnlyHint: true. The LLM cannot write to UACAPI.

Tool Purpose Auth
search_products Catalog search with query, filters, sort, price range Shopper token
get_orders Order history with status, items, totals Integration token + customerNo
get_order_detail Order detail with shipment tracking data Integration token + customerNo
create_support_ticket Intercepted — renders deterministic ticket form User email from headers
request_user_input Renders chips, text inputs, confirm buttons N/A

Security and Trust

Enterprise-grade security built into every layer. The model never sees credentials. Tools are read-only. Ticket creation is deterministic.

Security by Design

🔒
Read-Only Tools All MCP tools annotated readOnlyHint: true. The LLM cannot modify any data in UACAPI.
🛡️
No GraphQL Injection Static query documents and variables only. Never string interpolation.
🔑
Credential Isolation Shopper token for search. Integration token for orders. Tokens never cross boundaries.
🚫
Token Never Reaches LLM Auth injected only at the tool-call boundary. The model never sees credentials.
🏛️
Integration Token Server-Side The integration token lives only in backend environment config. Never reaches the browser.
📏
Bounded Sessions 20-turn limit, 500 session cap, trimmed assistant content to prevent context overflow.
📝
Deterministic Tickets LLM cannot create tickets directly. It triggers a fixed form — reliable every time.
📦
Stable Output Contracts Widget consumes mapped outputs, not raw UACAPI responses. Schema drift is isolated.
